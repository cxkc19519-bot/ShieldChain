# SAGA Feature-Source Matrix

This matrix is a release gate. Paper evidence goes only in `论文原始设计`; deterministic implementation choices go in `复现工程补充`; behavior that must not enter the base reproduction goes in `后续创新扩展`.

| 功能 | 论文原始设计 | 复现工程补充 | 后续创新扩展 |
|---|---|---|---|
| System participants and trust roles | Users own and manage Agents; the Provider maintains registries and enforces contact-policy decisions; Agents communicate directly after setup (III-B; IV-A; Fig. 1). The Provider follows the protocol but may be honest-but-curious (III-C-D). | Model the protocol core, Provider service, User actor, initiating Agent, and receiving Agent as distinct roles; do not claim protection from a malicious Provider. | Byzantine or malicious-Provider governance. |
| User identifier and persistent identity verification | A User chooses `uid_U`, obtains a CA certificate, and is verified through a persistent identity mechanism before registration (IV-B Steps 1-5; Fig. 7). | Expose an `IdentityVerifier` port with deterministic trusted test and local-demo adapters; do not claim to reproduce OpenID Connect. Phase 2 calls this port before certificate processing, password hashing, or registry creation and rejects failed identity evidence without creating a record. | Production identity-provider integration and stronger proof-of-personhood. |
| User signature key and certificate | The User generates a signing key pair and obtains `Cert_U` binding `uid_U` to the public key (IV-B Steps 1-2; Fig. 7). | Use a test CA and mature certificate/signature libraries. Phase 1 Task 9 validates User certificate DER, SPKI binding, the single-root URI-SAN BC/KU/EKU profile, and half-open validity only at the certificate boundary. Phase 2 consumes that validation boundary for `Cert_U` at registration; CA issuance and key generation remain preprovisioned inputs. | Hardware-backed User keys and external PKI profiles. |
| Provider identity, certificate, and signing key | The User retrieves and verifies the Provider certificate/public key for TLS; the Provider signs registered Agent information (IV-B Step 3; IV-C Step 7; Figs. 7-8). | Provision a test-CA X.509 identity and separate signing-key configuration for the Provider. Phase 1 Task 3 treats the tuple's `provider_public_key` as opaque non-empty bytes; Task 9 separately owns certificate DER parsing, SPKI binding, the single-root URI-SAN BC/KU/EKU profile, and half-open validity. | Multi-Provider trust anchors. |
| User Registry | The Provider stores the password-derived record and `Cert_U` in User Registry `D_U`, keyed by `uid_U` (IV-B Steps 5-6; Fig. 7). | Define a registry port, uniqueness checks, and secret-safe password-record persistence. Phase 2 implements atomic create-or-conflict and immutable reads with matching in-memory and SQLite User Registry outcomes, rollback, and restart coverage. | Federated User registries. |
| Agent identifier and Endpoint Descriptor | The User creates globally unique `aid_A` and endpoint descriptor `ED_A`, and the Provider verifies uniqueness (IV-C Steps 1, 5-7; Fig. 8). | Represent `aid_A = uid_U:name_A` and `ED_A = <device_A, IP_A, port_A>` as validated immutable values. Phase 2 enforces owner-prefix consistency and deterministic global Agent-ID and endpoint conflicts in both registry adapters. | Rich service discovery and capability advertisements. |
| Agent TLS credential and certificate | The User creates Agent TLS credentials and `Cert_A`; the Provider verifies the certificate during registration and peers verify certificates during communication (IV-C Steps 1-2, 5-6; IV-E Steps 3-6; Figs. 8-9). | Use test-CA X.509 certificates and real TLS endpoints. Phase 1 Task 3 treats `agent_tls_public_key` and `agent_certificate` tuple members as opaque non-empty bytes; Task 9 exclusively owns certificate DER parsing, SPKI binding, the single-root URI-SAN BC/KU/EKU profile, and half-open validity. Phase 2 consumes the closed Agent certificate boundary during registration; peer TLS verification is deferred network evidence. | Production CA enrollment and automated rotation. |
| Agent long-term access-control key | Each Agent has long-term access-control keys `(PAC_A, SAC_A)`; the public key is registered and the secret remains local (IV-C Steps 2, 5-7; IV-E Steps 5-7; Figs. 8-9). | Represent the pair with X25519 keys and prevent secret-key serialization or logging. Phase 2 validates and persists only the 32-byte public `PAC_A`; it does not accept or store `SAC_A`. | Hardware-backed access-control secrets. |
| OTK public/secret key pair | The User generates `(OTK_A^i, SOTK_A^i)` pairs, registers signed public OTKs, and keeps SOTKs at the Agent (IV-C Step 2 and Step 5; Fig. 8). | Generate X25519 pairs with explicit available/issued/consumed lifecycle state. Phase 2 stores verified public OTK registration material only; Phase 3 owns lifecycle and allocation, and no SOTK is accepted or persisted. | Risk-adaptive OTK pool sizing. |
| User signature over Agent metadata | `sigma_A^U` signs the Agent identifier, endpoint, TLS public key, access-control public key, and Provider public key (IV-C Steps 2 and 6; Fig. 8). | Encode the exact signed tuple canonically and reject any field tampering. Phase 2 verifies the exact canonical metadata tuple with the validated User public key before any Agent Registry write. | Additional signed capability metadata. |
| User signature over each OTK | `sigma_OTKi^U` signs each tuple containing `aid_A` and `OTK_A^i`; the Provider and initiating Agent verify it (IV-C Steps 2, 5-6; IV-E Step 3; Figs. 8-9). | Canonically serialize and verify every OTK independently. Phase 2 verifies every registered public OTK signature before committing the complete batch. | Batch or post-quantum OTK attestations. |
| Provider signature over Agent registration information | The Provider signs the IV-C Step 7 main-text tuple containing `aid_A`, `Cert_A`, `ED_A`, `PAC_A`, and `sigma_A^U` (IV-C Step 7); Appendix Fig. 8 has a conflicting layout. | Follow the IV-C Step 7 formula and record the Fig. 8 discrepancy in the ambiguity register. Phase 2 returns an attestation over the main-text tuple only after User verification and before the atomic create; it does not persist the Provider attestation in `D_A`. | Versioned registration attestations. |
| Agent Registry | The Provider stores User ownership, Agent metadata, Contact Policy, User signatures, and public OTKs in `D_A` (IV-C Step 7; Fig. 8). | Define uniqueness, ownership, and transactional registry ports. Phase 2 implements atomic complete Agent-plus-public-OTK writes in memory and SQLite, with rollback, restart, and no partial-record observability. Active state is entirely deferred to Phase 3. | Cross-Provider registry federation. |
| Contact Policy rule syntax | A Contact Policy is a set of Agent-ID patterns paired with OTK budgets (IV-D.1; Listing 1). | Validate exact/user-domain/Agent-type/global patterns; reserve `budget=-1` as deny. Phase 2 preserves the registration document as bounded opaque UTF-8 only; matching and budgets remain Phase 3. | Attribute-, context-, or risk-based rules. |
| Contact Policy specificity | When rules match, the most specific matching rule determines the budget (IV-D.1; Listing 1; `Budget_OTK` definition). | Order exact Agent ID above user-domain wildcard, Agent-type wildcard, and global wildcard; reject equal-specificity overlap. | Policy-combining algorithms. |
| Pair OTK budget counter | On first `(receiving, initiating)` contact, the Provider initializes `Counter_OTK[aid_A][aid_B]` from the selected policy budget and decrements it on issuance (IV-D.2; IV-E Step 2). | Persist the pair counter; distinguish no match, deny, and exhausted budget; policy updates never restore consumed quota. | Risk-adaptive pair budgets. |
| Single-OTK-per-request allocation | The Provider deliberately returns only one OTK per request to limit the compromise window (IV-D.2; IV-E Step 2). | Enforce exactly-one allocation within the contact-resolution transaction. | Explicitly negotiated OTK batches outside the baseline. |
| OTK public-key consumption | Each public OTK is one-time and is returned once after policy and counter checks (IV-D.2; IV-E Step 2). | Atomically mark the selected public OTK consumed so it cannot be reissued, including under concurrency. | Recoverable or threshold OTK mechanisms. |
| Receiving Agent SOTK deletion | After DH and KDF, the receiving Agent deletes the used OTK-to-SOTK mapping before generating the Token, enforcing one-time use (IV-E Step 6; Fig. 9). | Persist the consumed state and perform the deletion as an atomic, fail-closed state transition. | Hardware-enforced erasure. |
| Policy update | Users may add/remove policy rules and push updates through the Provider (IV-D, “Policy Updates and Revocation”). | Apply new rules immediately to new OTK requests; recompute specificity and cap remaining pair quota at `min(old remaining, new budget)` without restoring spent quota. | Retroactive policy actions on issued ACTs. |
| Agent deactivation | A User may deactivate only an Agent they own, disabling incoming contact (IV-D, “Policy Updates and Revocation”). | Make deactivation transactional and block discovery/new OTK issuance while preserving an auditable state transition. | Cross-Provider deactivation propagation. |
| Receiving Agent lookup | The initiating Agent submits both Agent identities; after policy/quota checks the Provider returns the receiver's certificate, endpoint, access-control public key, signed OTK, and signed metadata (IV-E Steps 1-3; Fig. 9). | Return a typed response only after one atomic policy/active/budget/OTK decision. | Privacy-preserving discovery. |
| Agent-to-Provider TLS | The initiating Agent establishes TLS with the Provider before lookup (IV-E Step 1; Fig. 9). | Use real X.509-authenticated TLS in the transport adapter and end-to-end tests. | Provider transparency and channel attestation. |
| Agent-to-Agent mutual TLS | The initiating and receiving Agents establish TLS and verify each other's Agent certificates (IV-E Step 4; Fig. 9). | Configure mutual TLS with test-CA trust, hostname/identity checks, timeouts, reconnect tests, and no protocol logic in routes. | Channel binding to hardware attestation. |
| X25519 shared-secret derivation | Both Agents compute equivalent DH secrets from the initiator's long-term access-control key and receiver's OTK/SOTK (IV-E Step 6; Fig. 9). | Instantiate the abstract DH operation with X25519 and fixed test vectors. Phase 1 implements this supplement in `src/saga/crypto/key_agreement.py` with RFC 7748 equality vectors; PAC/OTK public values use raw X25519-32 bytes. | Hybrid post-quantum key agreement. |
| HKDF shared-key derivation | Both Agents apply a KDF to the DH result to obtain the same `SDHK` (III, KDF background; IV-E Step 6; Fig. 9). | Use HKDF-SHA256 with the fixed salt/info parameters classified below. Phase 1 implements the fixed-domain `derive_sdhk` wrapper and consumes a public deterministic vector. | Negotiated KDF suites. |
| ACT creator, encryptor, holder, and verifier | Receiving Agent A creates, encrypts, stores, and verifies ACT state; initiating Agent B holds the ciphertext and attaches it to later requests (IV-E Steps 7-8; Fig. 9). | Keep receiver-side usage state and initiator-side ciphertext separate; never log plaintext or shared keys. | Delegated or multi-verifier tokens. |
| ACT plaintext fields | The ACT plaintext contains only `nonce`, `issued_at`, `expires_at`, `q_max`, and `initiating Agent access-control public key` (IV-E Step 7; Fig. 9). | Encode exactly these five fields; do not add version, token ID, Agent IDs, task ID, context hash, tool, operation, parameter, or resource fields. | Task/tool/resource constraints belong only to a future token family. |
| ACT initiating-Agent binding | The initiating Agent access-control public key in the ACT binds use to the intended initiator, and the receiver rejects another Agent (IV-E Steps 7-8; Fig. 9; Appendix E A5; Table IV). | Map the mTLS-authenticated peer to its registered access-control public key and compare with constant-time semantic equality. | Stronger channel or device binding. |
| ACT lifetime | The ACT carries issue and expiration times and is valid only before expiration (IV-E Steps 7-8; Token reuse; Fig. 9). | Use an injectable Clock and half-open validity interval `[issued_at, expires_at)`. | Risk-adaptive lifetime. |
| ACT q_max | The ACT sets a maximum request count and the receiver rejects use beyond the quota (IV-E Steps 7-8; Token reuse; Fig. 9). | Persist receiver-side count and perform an atomic `< q_max` check-and-increment. | Dynamically adjustable quota. |
| ACT legal reuse | The initiator may reuse the same valid ACT until expiration or quota exhaustion without returning to the Provider (IV-E “Token reuse”; Fig. 1; Fig. 9). | Test reuse explicitly, including TLS reconnection, and do not misclassify valid reuse as replay. | Per-request proof or idempotency semantics. |
| ACT task-completion discard | Both Agents discard the ACT when the task completes (IV-E Step 8; Fig. 9). | Expose explicit local discard at both parties; recontact requires a fresh OTK/ACT. | Verifiable completion receipts. |
| Existing ACT after policy update/deactivation | Policy changes and deactivation govern future contact/OTK issuance, but the paper does not define retroactive invalidation of already issued ACTs (IV-D; IV-E Token reuse; Fig. 9). | Existing ACTs expire naturally or exhaust `q_max`; do not add a revocation list to the baseline. | Active revocation of issued ACTs. |
| Replay semantics | TLS is assumed to mitigate network-record replay, while the ACT is intentionally reusable within lifetime and quota (III-C; IV-E Step 8 and Token reuse; Fig. 9; Appendix E A3/A5; Table IV). | Separate TLS-record replay, legal ACT reuse, wrong-Agent transfer, and expired/exhausted reuse in tests; do not claim application-request deduplication. | Request IDs, idempotency keys, and semantic replay detection. |
| Canonical serialization | The paper fixes signed/encrypted tuples but does not specify a byte serialization (IV-C Steps 2, 6-7; IV-E Step 7). | Use deterministic JSON with UTF-8, fixed field order, and no floating-point security fields. Phase 1 implements closed schemas and byte-exact vectors in `src/saga/crypto/canonical.py`; Task 3 keeps certificate/TLS-key tuple members opaque, while DER validation remains exclusively at Task 9's certificate boundary. | Standards-based canonical encodings. |
| Protocol outer version | No version field appears in the ACT plaintext tuple (IV-E Step 7; Fig. 9). | Put `version` only in the outer protocol message and reject unsupported versions. | Cryptographic-suite negotiation. |
| Base64URL binary encoding | The paper leaves wire encoding of keys, signatures, nonces, and ciphertext unspecified (IV-C-E). | Encode binary fields as unpadded Base64URL with strict decoding. | Alternative negotiated binary encodings. |
| Integer time representation and injectable Clock | The paper specifies issue and expiration timestamps but not their wire unit or test clock (IV-E Steps 7-8; Fig. 9). | Use integer Unix milliseconds and an injectable Clock; avoid `sleep`-based time tests. | Trusted-time attestations. |
| Ed25519 choice | The protocol requires secure signatures and signature verification but does not mandate Ed25519 at the protocol layer (III, signatures; IV-B-C). | Use Ed25519 for User and Provider signatures and classify it as an engineering choice. Phase 1 implements the mature-library wrapper and public vectors in `src/saga/crypto/signatures.py`; `PK_Prov` is a raw 32-byte Ed25519 public key. | Algorithm agility and post-quantum signatures. |
| ChaCha20-Poly1305 choice and AAD | The ACT is abstractly encrypted under `SDHK`; the paper does not specify an AEAD or AAD (IV-E Step 7; Fig. 9). | Use ChaCha20-Poly1305 with `aad=b"SAGA-ACT/v1"`; reject nonce/ciphertext/AAD tampering. Phase 1 implements the closed versioned envelope in `src/saga/crypto/aead.py` and keeps the outer version and AEAD nonce outside the exact five-field ACT plaintext. | Negotiated AEAD suites. |
| HKDF salt/info domain separation | The paper derives `SDHK` with a KDF and describes HKDF-SHA256, but does not define salt/info domain separation (III, KDF background; IV-E Step 6). | Use HKDF-SHA256 with `salt=None` and `info=b"SAGA-ACT-DERIVE/v1"`. Phase 1 fixes the output length at 32 bytes and exposes no caller-controlled salt, info, or length. | Per-tenant or transcript-bound derivation contexts. |
| scrypt password record | The Provider stores a hash-derived password record and should follow password-management best practices (IV-B Steps 5-6; IV-D cryptographic key management; Fig. 7). | Use scrypt with `N=2^15, r=8, p=1, dkLen=32` and a fresh 16-byte random salt. Phase 1 implements the versioned, redacted persistence record in `src/saga/crypto/passwords.py`; it is supported only through `saga.crypto.passwords` and is not a top-level result DTO. Phase 2 creates it after successful identity/certificate checks and verifies it before Agent registration, while keeping it internal to the User Registry. | External passwordless authentication. |
| Stable domain error taxonomy | The paper distinguishes policy no-match, OTK-pool exhaustion, pair-quota exhaustion, invalid credentials/signatures, inactive Agents, and invalid ACT conditions (IV-B-E; IV-F). | Define stable fail-closed domain errors and map them to transport status without exposing verification or secret-state oracles. Phase 2 uses closed registration input, identity, owner-authentication, verification, conflict, and persistence outcomes without propagating backend exception details. | Cross-organization error federation. |
| Structured secret-safe logging | The paper does not prescribe application logging; its threat model requires protecting credentials, keys, registries, and tokens (III-C-D). | Log event, public entity IDs, result class, duration, and correlation ID only; never log passwords, private keys, SOTKs, `SDHK`, or ACT plaintext. Phase 2 freezes only the secret-safe `RegistrationEvent` DTO schema; no logger or event sink is implemented or claimed. | Privacy-preserving distributed audit ledger. |
| Atomic OTK allocation | The protocol requires selecting and returning a one-time OTK after checks (IV-D.2; IV-E Step 2), but does not define concurrency control. | Perform select-and-consume in one linearizable transaction so concurrent requests cannot receive the same OTK. | Distributed atomic allocation across shards. |
| Atomic pair-budget decrement | The Provider checks a positive pair counter and decrements it after OTK issuance (IV-D.2; IV-E Step 2), but does not define concurrency control. | Combine policy read, active check, counter check/decrement, and OTK consumption in one transaction. | Distributed quota consensus. |
| Atomic q_max check-and-increment | The receiver rejects ACT use beyond the request quota (IV-E Step 8; Token reuse), but persistent counting and concurrency are unspecified. | Atomically check `< q_max` and increment successful use; for `q_max=1`, only one concurrent request succeeds. | Distributed ACT-use accounting. |
| In-memory persistence adapter | Registries and counters are protocol state (IV-B-E); the paper does not require an in-memory adapter. | Provide deterministic in-memory implementations of registry, OTK, pair-counter, and ACT-state ports for unit/protocol tests. Phase 2 implements thread-safe User and Agent registration registries with atomic uniqueness outcomes only; OTK allocation, pair counters, and ACT state remain deferred. | Replicated in-memory state. |
| SQLite persistence adapter | The paper requires persistent registries but does not mandate SQLite (III-B; IV-B-D). | Provide a SQLite adapter with transactions, uniqueness constraints, crash persistence, and the same domain semantics as memory. Phase 2 implements User and complete Agent-plus-public-OTK registration transactions, rollback, structural read failure closure, and restart parity only. | Distributed SQL persistence. |
| FastAPI transport adapter | The paper implementation exposes HTTPS endpoints but does not mandate FastAPI (VI-A). | Use thin FastAPI routes that validate transport input, call protocol services, and map domain errors without embedding authorization decisions. | Alternative transports and service meshes. |
| ProVerif token-secrecy query | The paper formally analyzes ACT/token secrecy against a network attacker (IV-F; Appendix D). | Maintain an isolated ProVerif communication model and record tool/version/results without claiming implementation-level secrecy proof. | Stronger compromise and malicious-Provider models. |
| ProVerif Agent-Provider authentication query | The paper analyzes authentication between Agents and the Provider (IV-F; Appendix D). | Model injective authentication/correspondence for registration and Provider interactions, plus reachability. | Byzantine-Provider authentication. |
| ProVerif Agent-Agent authentication query | The paper analyzes authentication between communicating Agents (IV-F; Appendix D). | Model bilateral Agent authentication and reachability separately from runtime mTLS tests. | Multi-hop or delegated authentication. |
| Twenty required security tests | The paper evaluates eight adversarial cases A1-A8 and identifies their detection points (IV-F; Appendix E; Table IV). | Expand coverage to the twenty project-required security tests and label each as direct paper evaluation, threat-model inference, or engineering hardening. | Future attacks receive new rows before implementation. |
| Directional performance acceptance | The paper evaluates OTK generation, Token derivation, and protocol overhead (VI-B-VI-C; Figs. 2-5), plus Provider throughput/capacity, RAFT, Agent registration, and OTK refresh (VI-D; Fig. 6; Figs. 10-12). | Accept reproducible directions rather than cross-hardware absolute numbers; capture environment, samples, mean/median/P95/P99/stddev, CSV/JSON, and explain deviations. | Broader production-scale SLOs. |
| RAFT/Paxos fault tolerance |  |  | Paper extension: replicated Provider fault tolerance using RAFT is specified in V-A and evaluated in VI-D (Fig. 6; Figs. 10-12); RAFT/Paxos replication is excluded from the base reproduction. |
| Provider sharding and federation |  |  | Paper extension: Provider sharding/scalability is specified in V-A and evaluated in VI-D (Fig. 6); sharding and federation are excluded from the base reproduction. |
| A2A integration |  |  | Paper extension: A2A interoperability is specified in V-B; integration is excluded from the base reproduction. |
| Agent-to-Tool Capability Token |  |  | Future innovation only: define a separate capability token and branch for Agent-to-Tool authorization; do not add tool, action, parameter, or resource fields to the base ACT. |
| Risk-adaptive Token policy |  |  | Future innovation only: adapt Token lifetime, quota, or OTK budget to measured risk after the baseline stability gate. |
| Prompt-injection detector |  |  | Future innovation only: add prompt-injection detection as an independent defense layer after the baseline; do not attribute it to SAGA protocol security. |
| Active Token revocation list |  |  | Future innovation only: add active revocation of issued ACTs after the baseline; the base reproduction uses natural expiry or quota exhaustion. |
