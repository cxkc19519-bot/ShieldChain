# 网络协议与流量分析基础（2026-09）

> 版本：2026.09.0｜最后核验：2026-09-09｜下次复核不晚于：2026-10-02｜复核角色：网络检测知识库管理员｜资料属性：内部安全知识库。本文用于防御性流量分析，不把单一网络特征直接解释为攻击成功。

## 1. 从连接事实开始

网络流量研判至少记录时间、传输协议、源和目的地址、端口、方向、字节与报文数、连接状态、传感器位置及采集完整性。TCP 是面向连接的可靠字节流协议，分析 SYN、ACK、FIN、RST、重传和连接持续时间能够描述会话行为，但不能仅凭某个标志位给攻击定性。半开连接集中出现可能来自扫描、拥塞、故障或采集不完整，必须结合基线和其他日志判断。

TCP 的规范基线采用 IETF RFC 9293：https://www.rfc-editor.org/rfc/rfc9293.html

## 2. DNS 观测

DNS 日志应保留查询时间、客户端、查询名、类型、响应码、答案、TTL、解析器和传输方式。大量不存在域名、异常长标签、高熵子域、罕见记录类型或固定周期查询是调查线索，不是恶意结论。需要排除软件更新、内容分发、遥测、反垃圾邮件查询和安全产品主动探测。

调查时把域名解析结果与后续连接、证书、进程、资产角色和历史首次出现时间关联。只看到 DNS 查询不能证明客户端成功连接，更不能证明数据已经外传。

DNS 消息和资源记录基础采用 RFC 1035：https://www.rfc-editor.org/rfc/rfc1035.html

## 3. HTTP 与反向代理日志

HTTP 研判关注方法、目标 URI、Host、状态码、请求与响应大小、内容类型、用户代理、转发链、认证主体和上游处理时间。单个 4xx/5xx 可能是正常错误；短时间遍历大量路径、异常方法组合、同一来源重复触发输入校验、成功响应后紧跟异常进程或外连才更值得关联。

代理链中的客户端地址必须根据受信代理配置解析，不能无条件相信外部可控的转发头。URI、查询参数和请求体可能包含凭据或个人信息，日志采集应做最小化、脱敏和权限控制。

HTTP 语义采用 RFC 9110：https://www.rfc-editor.org/rfc/rfc9110.html

## 4. TLS 加密流量

TLS 加密后通常仍可观察连接两端、时间、流量体积、握手结果和部署允许采集的证书元数据。证书过期、名称不匹配、握手失败激增、罕见服务端或异常周期连接可作为线索，但自签名证书在实验、内网设备和开发环境中可能是预期行为。

不得把“看不见明文”解释为恶意，也不得为了检测而默认解密全部业务流量。解密必须有明确授权、数据保护边界和审计记录。

TLS 1.3 规范采用 RFC 8446：https://www.rfc-editor.org/rfc/rfc8446.html

## 5. 常见流量行为与最小验证

- 扫描：多个端口或目标的短连接。验证来源资产、失败比例、维护窗口和后续成功会话。
- 暴力尝试：同一身份或服务连续失败。关联认证日志、来源变化、成功登录和 MFA 事件。
- 信标：相近周期、相似字节量的外连。排除监控、更新时间同步和健康检查。
- 横向活动：内部管理协议出现新来源或新目标。关联账号、端点进程、工单和资产管理记录。
- 数据外传：异常出站体积或目的地。先核对备份、同步、发布和批处理任务，再检查数据敏感度与进程来源。

每个结论都应区分观测事实、推断、替代解释和未知项，并保留原始流量或不可篡改摘要以便复核。
